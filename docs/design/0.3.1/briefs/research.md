## 1. What `pmset -a disablesleep 1` actually does

**Key and write path**
- [C] `pmset` takes `disablesleep N` and stores `kIOPMSleepDisabledKey` (`"SleepDisabled"`) = true/false in a *system-wide* dictionary. The parser never looks at the `-a/-b/-c/-u` flags for this key, so `-b`/`-c` scoping does nothing: the setting is always global. Source: `pmset/pmset.m` lines ~5813–5836 (and the comment at ~5107: "system-wide settings, not tied to power source. like 'disablesleep'"). https://github.com/apple-oss-distributions/PowerManagement/blob/main/pmset/pmset.m
- [C] `pmset` writes it with `IOPMSetSystemPowerSetting()` (pmset.m ~802: "We write the settings to disk here; PM configd picks them up"). That function refuses unless uid/euid is 0 (`kIOReturnNotPrivileged`, and pmset prints "must be run as root"). It merges the key into the `SystemPowerSettings` dictionary in the CFPreferences domain `com.apple.PowerManagement` (kCFPreferencesAnyUser and CurrentHost), runs `CFPreferencesSynchronize`, then posts `kIOPMPrefsChangeNotify`. Source: `pwr_mgt.subproj/IOPMEnergyPrefs.c` ~1604–1660, `IOPMLibPrivate.h` ~1682–1684. https://github.com/apple-oss-distributions/IOKitUser/blob/main/pwr_mgt.subproj/IOPMEnergyPrefs.c
- [C] powerd (`pmconfigd/PMSettings.m`, `PMActivateSystemPowerSettings` ~1330) reads that preference and sets the `SleepDisabled` property on `IOPMrootDomain` with `IORegistryEntrySetCFProperty`. In the kernel (`IOPMrootDomain.cpp` ~2055 and ~8388), that sets `userDisabledAllSleep`. https://github.com/apple-oss-distributions/PowerManagement/blob/main/pmconfigd/PMSettings.m · https://github.com/apple-oss-distributions/xnu/blob/main/iokit/Kernel/IOPMrootDomain.cpp
- [C] On-disk location seen in the field: `/Library/Preferences/com.apple.PowerManagement.plist` → `SystemPowerSettings` → `SleepDisabled` (Williams College lab note; a derflounder comment says it moved there in 10.12). https://sites.williams.edu/lj1/labs/macos-disabling-sleep-option-from-finder-menu/ · https://derflounder.wordpress.com/2013/01/27/disabling-the-sleep-command-in-the-apple-menu/ [U] The man page still names `/Library/Preferences/SystemConfiguration/com.apple.PowerManagement.plist` for pmset settings in general. The exact file that CFPreferences AnyUser/CurrentHost resolves to on 14/15/26 was not checked on a real Mac. https://keith.github.io/xcode-man-pages/pmset.1.html
- [C] `disablesleep` does not appear in the `pmset(1)` man page. It is undocumented. https://keith.github.io/xcode-man-pages/pmset.1.html

**Persistence across reboot**
- [C, from source] It persists. At startup powerd's `PMSettings_prime()` calls `PMActivateSystemPowerSettings()`, commented "Activate non-power source specific, PM settings namely disable sleep, where appropriate" (PMSettings.m ~1160). That re-applies the stored `SleepDisabled` at every boot. `pmset restoredefaults` does not clear it either. Apple Community thread, macOS 14.0 on an M1 Max: https://discussionschinese.apple.com/thread/255756222
- [U] **Conflicting claim:** the Sleepless app (Aboudjem) says "`disablesleep` is a runtime setting. A reboot restores normal sleep… toggle on, reboot, then `pmset -g | grep SleepDisabled` should read 0." https://github.com/Aboudjem/Sleepless (SECURITY.md). This contradicts Apple's published source. Insomnia, by contrast, treats a reboot as a recovery case and validated "Reboot/login with active or dirty journals" on an M5 running macOS 26.2 (docs/release-validation.md). **[D] Design as if it persists, and test it on a real Mac on 14, 15 and 26.**

**Visibility**
- [C] `pmset -g` is an alias for `pmset -g live` (pmset.m ~570: an empty argument returns `ARG_LIVE`). It prints a `System-wide power settings:` header and then ` SleepDisabled\t\t0|1`, but only when the key exists in the stored dictionary (pmset.m ~1184–1199). On a Mac that never set it, the line is absent. After `disablesleep 0` it reads `0`. **Note:** this line comes from the *preference*, not from the kernel.

**What it blocks** (kernel logic is shared by Intel and Apple silicon builds)
- [C] `checkSystemSleepAllowed()` returns "not allowed" as soon as `userDisabledAllSleep` is set (error `kPMUserDisabledAllSleep`, "user-space sleep kill switch"). This check runs **before** the later exceptions for low battery and thermal ("always sleep on low battery or when in thermal warning/emergency state"). `privateSleepSystem()` calls `checkSystemSleepEnabled()` → `checkSystemSleepAllowed(0,0)` and returns `kIOReturnNotPermitted`. Source: IOPMrootDomain.cpp ~2899–2912 and ~7666–7785.
  - Lid close: clamshell sleep goes through `privateSleepSystem(kIOPMSleepReasonClamshell)` (~8890), so **it is blocked** whatever the power source and whether or not a display is attached. [C, source] Field reports confirm this on Apple silicon on battery with no external display: Insomnia (M5, macOS 26.2, lid-close checks passed) and Sleepless ("verified live… disables idle + Apple-menu + lid-close clamshell sleep", macOS 26). [U] No first-hand Intel report on macOS 14/15 was found. The kernel path is the same.
  - Apple menu › Sleep and `pmset sleepnow`: both go through `sleepSystemOptions` → `privateSleepSystem` → refused. [C] derflounder (2013, Intel) reports that Sleep is **greyed out** in the Apple menu, and a Jamf thread says SleepDisabled "does remove the sleep option from the menu". https://community.jamf.com/general-discussions-2/ad-bind-issues-sierra-and-removing-sleep-14627 [U] Exact menu UI on 26 is unverified.
  - Thermal emergency: `kIOPMOverTemp` → `privateSleepSystem(kIOPMSleepReasonThermalEmergency)` (~8674) → **refused**. The dark-wake thermal path goes through `checkSystemCanSleep` and is refused too. [C, source] **The OS will not put the Mac to sleep for heat while SleepDisabled=1.** [U] Hardware or firmware thermal trips (forced power-off) and CPU throttling presumably still happen. Not documented by Apple. One HN commenter: "it will overheat and shut down anyway." https://hn.svelte.dev/item/48701512
  - Low battery: `kIOPMPowerEmergency` (~8691–8717). On Intel, and on arm64 when secure hibernation is supported, it calls `privateSleepSystem(kIOPMSleepReasonLowPower)` → **refused**. On arm64 when `!ml_is_secure_hib_supported()` (or Lockdown Mode), the kernel instead sends `kIOPMMessageRequestSystemShutdown`, and powerd calls `reboot3(RB_HALT)` (pmconfigd.m ~1602). SleepDisabled does not gate that path. [C, source] [U] Which Apple silicon Macs take which branch is unknown. **[D] Assume no emergency sleep. The battery may run to hardware cutoff (an abrupt power-off), so the watchdog must enforce a battery floor.**
- [C] With SleepDisabled set, closing the lid no longer turns the internal panel or keyboard backlight off by itself (Insomnia docs/lid-close.md). Amphetamine 5.3 forces the built-in display to sleep when the lid is closed on Apple silicon (changelog). **[D] On lid close, run `pmset displaysleepnow` (no root needed) or a display-sleep assertion. Otherwise the panel stays lit inside the closed lid, which adds heat and drains the battery.**
- [C] Another keep-awake tool can reset the bit underneath you. Insomnia saw a root LaunchDaemon from another tool run `pmset -a disablesleep 0` every 2 s, so it now reads `pmset -g` back 5 s after setting (Sources/Insomnia/Core/SleepGuard.swift).

**macOS 14/15/26 changes**
- [U] No documented change to `disablesleep` was found. The key exists on 14.0 (Apple Community thread above) and works on 26.x (Insomnia, Sleepless, Adrafinil). Insomnia notes that **macOS 27** dropped `lowpowermode` from `pmset -g custom` output in favour of `powermode` (SleepGuard.swift), so parse defensively.

## 2. Non-persistent alternatives

- [C] `caffeinate`, `pmset noidle` and IOPM assertions only prevent *idle* sleep. The man page says `noidle` is deprecated in favour of `caffeinate`, and that `caffeinate -s` works only on AC. KeepingYouAwake (a caffeinate wrapper) states it does not work with a closed lid. https://cdn.jsdelivr.net/gh/newmarcel/keepingyouawake@main/README.md
- [C] `pmset -b/-c disablesleep` is *not* scoped (see §1). It still writes the global key.
- [C] Writing `SleepDisabled` directly on IOPMrootDomain (`IORegistryEntrySetCFProperty`) needs the private `kRootDomainEntitlementSetProperty` entitlement. Root alone gets `kIOReturnNotPermitted` for anything except the six schedule keys (IOPMrootDomain.cpp ~1943–1975). Not viable.
- [C] **The one real non-persistent option** is the root-domain user-client call `kPMSetClamshellSleepState` with input 1. It has no entitlement check, needs only local-user privilege, and sets `clamshellSleepDisableMask |= kClamshellSleepDisablePowerd` in kernel memory, which is gone after reboot (RootDomainUserClient.cpp ~388, ~525; IOPMrootDomain.cpp ~4541, ~4461). Amphetamine's CDMManager uses exactly this (`IOConnectCallScalarMethod(conn, kPMSetClamshellSleepState, …)`). https://github.com/x74353/Amphetamine-Enhancer/blob/master/Xcode%20Project/CDMManager/CDMManager/AppDelegate.m. Caveats:
  - It only blocks *clamshell* sleep, so you still need an idle-sleep assertion. Apple menu Sleep still works.
  - powerd owns the same bit. `evaluateClamshellSleepState()` (PMAssertions.c ~1400–1470) rewrites it when its own computed state changes between zero and non-zero (on desktop-mode or assertion changes, and on power-source changes from BatteryTimeRemaining.m ~918). That explains why Amphetamine 5.3 notes "Apple changed the way Closed-Display Mode works on Apple Silicon… sessions could fail when the power source changed". The fix needed an admin script, and **Power Protect** (5.3.1) runs it without a password on Apple silicon laptops. https://mac.softpedia.com/progChangelog/Amphetamine-Changelog-140109.html
  - The dark-wake evaluation (IOPMrootDomain.cpp ~9150) sleeps a closed-lid Mac on battery regardless of this mask once it falls into dark wake. [U] How reliable this is on battery on 14–26 is unknown.
  - It needs compiled code, not a shell command (it could live in the app itself).
- [D] Conclusion: no shell-level non-persistent equivalent exists. Keep `disablesleep` and engineer for persistence (§5).

## 3. How other apps do it

**Insomnia (krishhgg)** ([C], repo files cited)
- Install (`scripts/install.sh` ~386–410) writes `/etc/sudoers.d/insomnia`, checked with `visudo -cf`:
  ```
  $USER ALL=(root) NOPASSWD: /usr/bin/pmset -a disablesleep 1
  $USER ALL=(root) NOPASSWD: /usr/bin/pmset -a disablesleep 0
  $USER ALL=(root) NOPASSWD: /usr/bin/pmset -b lowpowermode 1
  $USER ALL=(root) NOPASSWD: /usr/bin/pmset -b lowpowermode 0
  ```
  The app calls `sudo -n` with a 20 s timeout and never SIGKILLs a running root pmset. README warns that any process running as the user can use the rule.
- Sessions are always timed (max 30 days). A JSON recovery journal (`state.json`, `sleepDisabledByUs`) is written and a launchd backstop armed **before** `pmset -a disablesleep 1`. It reads back after 5 s and aborts if the value reverted (docs/spec.md §1).
- Safety (app alive only): on battery, Low Power Mode below 40% and session end below 10% (both configurable). An unreadable battery level on two reads in a row ends the session. Thermal `serious` → Low Power Mode, `critical` → end session (via `ProcessInfo.thermalStateDidChangeNotification`). Lid close → Low Power Mode, display and keyboard backlight off, selected apps SIGSTOPped, audio muted (spec §6, README).
- Crash: a per-user LaunchAgent (`RunAtLoad` + `StartInterval 60`) runs `backstop.sh`, signature-verified against the bundle, **only after the session deadline passes**. It undoes journaled entries with `sudo -n pmset -a disablesleep 0` and does **not** watch battery or heat ("The recovery agent doesn't watch the battery or the temperature"). At launch with no journal, a `SleepDisabled 1` is treated as someone else's and only reported, never cleared. Requires macOS 26, Apple silicon. README: "Use a stable, well-ventilated surface, not a closed bag."

**Sleepless (Aboudjem)** ([C]): sudoers drop-in `<you> ALL=(root) NOPASSWD: /usr/bin/pmset -a disablesleep 0, /usr/bin/pmset -a disablesleep 1`, installed through `osascript … with administrator privileges` running `grant.sh`. It has a battery-floor auto-off (default 15%), Low-Power-Mode auto-off and a 1–2 h timer, all in-memory with no daemon. It relies on the (contested) reboot reset. https://github.com/Aboudjem/Sleepless

**Amphetamine / Enhancer** ([C] where cited): Amphetamine is sandboxed (Mac App Store). Closed-display mode uses `kPMSetClamshellSleepState`. Its built-in safety includes auto-ending CDM sessions "under certain conditions" (5.2) and battery-percentage deactivation. Enhancer's fail-safe `amphetamine-enhancer-cdmManager.sh` checks `defaults read com.if.Amphetamine cdmEnabled`, and if Amphetamine is not running or holds no assertion, it launches CDMManager to clear the clamshell bit. https://github.com/x74353/Amphetamine-Enhancer. [U] What the 5.3 "script" and Power Protect "configuration file" contain is not public. The changelog says it requires "admin user authentication (Touch ID, Apple Watch, etc.)" or, with Power Protect, none, which implies a sudoers-style file.

**InsomniaX** ([C]): a setuid-root `loader` kextloads `Insomnia_r11.kext` from `~/Library/Application Support/InsomniaX`, which was an LPE (Securify, 2017; unmaintained). "CPU Safety" polled SMC temperatures and re-enabled lid sleep above 90 °C (later 80 °C). https://securify.nl/advisory/insomniax-loader-allows-loading-of-arbitrary-kernel-extensions/ · https://mac.softpedia.com/progChangelog/InsomniaX-Changelog-21611.html. Not usable on modern macOS.

**Adrafinil** ([C], from the HN post): a root helper exposing a single `setSleepBlocked` call that uses `pmset disablesleep`, with a configurable thermal cutoff (around 60 °C) and a low-battery resume. https://hn.svelte.dev/item/48701512

## 4. `do shell script … with administrator privileges`

- [C] It runs the command as root via `/bin/sh` (bash in sh mode). It does not read shell rc files, inherits the parent's environment and working directory (for `osascript`, the caller's cwd), and recommends absolute paths. `sudo` inside it is "generally unnecessary and creates security holes". Apple TN2065: https://developer.apple.com/library/archive/technotes/tn2065/_index.html [U] Whether PATH is reset for the root shell is unverified. **Use absolute paths (`/usr/bin/pmset`, `/bin/kill`, …) and set PATH explicitly in the script.**
- [C] Caching: "Once a script is correctly authenticated, it will not ask for authentication again for five minutes. The elevated privileges and the grace period do not extend to any other scripts or to the rest of the system." It cannot be sent to another app with `tell`. AppleScript Language Guide: https://developer.apple.com/library/archive/documentation/AppleScript/Conceptual/AppleScriptLangGuide/reference/ASLR_cmds.html [U] Each `/usr/bin/osascript` launch is a new process, so **expect a fresh prompt on every start and every stop**.
- [C] `with prompt "…"` customises the reason text and has been available since 10.10 (Shane Stanley, MacScripter). https://www.macscripter.net/t/way-to-specify-text-in-macos-system-password-dialog/70611 [U] Exact dialog wording on 26 ("osascript wants to make changes…").
- Touch ID: [C] Quinn (Apple DTS) says the authorization plug-in "has a hard-coded check for Apple-signed code. If the requesting process's main executable is signed by Apple, it allows the use of Touch ID", and that `do shell script "true" with administrator privileges` showed a Touch ID dialog while his own app's `AuthorizationCopyRights` showed only a password dialog. https://developer.apple.com/forums/thread/106386 · policy confirmed in https://developer.apple.com/forums/thread/701118 (Feb 2022). [U] Because `/usr/bin/osascript` is Apple-signed, Snaptic → osascript should get Touch ID. Amphetamine 5.3's "admin user authentication (Touch ID, Apple Watch…)" supports this. Not tested here.
- [C] Apple discourages it: Quinn calls it "equivalent to `sudo`… intended to be used by system administrators, and not as API. If we could deprecate the AppleScript approach in the context of an app running an AppleScript, we would." (thread 701118).
- Hardened runtime and TCC: [U, reasoned] The hardened runtime does not restrict spawning `/usr/bin/osascript`. `do shell script` runs inside osascript's own process with no Apple event sent to another app, so no Automation (Apple Events) TCC consent should be needed. Do not wrap it in `tell application …`, which the Language Guide forbids anyway.
- [C] **EDR flagging:** Elastic's prebuilt rule "Apple Scripting Execution with Administrator Privileges" (medium) matches `osascript*with administrator privileges` when the **parent's code signature is untrusted or missing**. An ad-hoc-signed Snaptic would match. https://www.elastic.co/guide/en/security/current/apple-scripting-execution-with-administrator-privileges.html
- Timeout and cancel: [U] AppleScript `with timeout` applies to app-targeted events, not to in-process StandardAdditions. There is no documented timeout for an unanswered auth dialog. Cancel returns error −128 "User canceled." (commonly observed, not fetched). **[D] Put an app-side timeout on the osascript `Process` and treat a nonzero exit as "not enabled".**
- Background child: [C] TN2065: `do shell script "command &> file_path &"` "will return immediately… running in parallel", and `echo $!` gives the PID. Output **must** be redirected or the call waits. [U] Survival after osascript exits is not documented for the admin variant. In practice there is no controlling TTY, so no SIGHUP, and the child reparents to launchd. **[D] Use `/usr/bin/nohup … </dev/null >>log 2>&1 &`, `trap '' HUP`, and have the script record its own PID. Safer still: `launchctl bootstrap system` a non-persistent plist from `/var/run` or `launchctl submit`, so launchd owns the watchdog (untested).**
- Alternatives: [C] `AuthorizationExecuteWithPrivileges` has been deprecated since 10.7 (docs list availability "macOS 10.1–10.7"; "Use a launchd-launched helper tool and/or the Service Management framework"). https://developer.apple.com/documentation/security/authorizationexecutewithprivileges.md [U] Whether it still links and runs on 26/27 is unconfirmed, and it is unusable from Swift without dlsym. [C] `SMAppService.daemon`: Quinn: "you should be signing both your embedded helper and your app with the same Apple-issued code-signing identity… If… you are using ad hoc signing… you will see problems like this" (`SMAppServiceErrorDomain Code=1 "Operation not permitted"`). It also needs user approval in Login Items, and Quinn recommends macOS 15+. https://developer.apple.com/forums/thread/799910 → **Not viable for ad-hoc builds.**

## 5. Known risks

- [C] Apple: use Mac laptops "on a stable work surface that allows for good ventilation", within 10–35 °C ambient, not in bed or under bedding, not in parked cars. https://support.apple.com/en-us/102336. Above 35 °C ambient "can permanently damage battery capacity", and charging inside some cases "may generate excess heat". https://www.apple.com/batteries/maximizing-performance/
- [C] Because SleepDisabled blocks thermal-emergency sleep (§1), a closed bag means OS protection is reduced to throttling, then any hardware trip. HN users report bags heating up and say a backpack laptop "will overheat and shut down anyway". https://brianlovin.com/hn/44745897 · https://hn.svelte.dev/item/48701512. Insomnia and InsomniaX both added heat cutoffs for this reason.
- [C] Battery: low-battery emergency sleep is blocked (§1), so a deep discharge to hardware cutoff is possible (unsaved work lost, battery stress).
- [C/U] Stuck-on state: the setting persists in preferences (source) and survives `restoredefaults` (Apple Community). If the watchdog dies (reboot, kernel panic, power loss, `kill -9` of the root shell), nothing resets it, and the Mac then **never sleeps on lid close or from the Apple menu**. Insomnia shows a warning with `sudo pmset -a disablesleep 0`. [U] No public report specifically about "my Mac never sleeps since an app crashed" was found, but the mechanism makes it inevitable without recovery.
- [D] Mitigations: (a) at Snaptic launch, if SleepDisabled=1 and a Snaptic marker file exists with no live watchdog, offer a one-click reset (admin prompt); (b) during the same admin prompt, optionally install a tiny root LaunchDaemon with `RunAtLoad` that clears the bit at boot when no session marker exists (persistent install, which needs an uninstall path); (c) the watchdog needs its own battery floor (`/usr/bin/pmset -g batt`) and heat check ([U] `notifyutil -g com.apple.system.thermalpressurelevel`, or `pmset -g therm`, which prints "Thermal Warning Level = N" or "No thermal warning level has been recorded", pmset.m ~4143), plus a hard maximum duration; (d) restore only if Snaptic set it (record the prior value); (e) read back after 5 s.

## 6. Reading the current state without root

- [C] `pmset -g` → line ` SleepDisabled  0|1` under "System-wide power settings:". It is absent if never set, so treat absent as 0. This reflects the **stored preference** (pmset.m ~1184). Used by Insomnia and Sleepless.
- [C] Kernel-applied truth: the `SleepDisabled` boolean property on `IOPMrootDomain`, set by powerd at boot and on every change (PMSettings.m ~1346; kernel `setProperty` at IOPMrootDomain.cpp ~2057). Read it with `IORegistryEntryCreateCFProperty(IOServiceGetMatchingService(kIOMainPortDefault, IOServiceMatching("IOPMrootDomain")), CFSTR("SleepDisabled"), …)` or `ioreg -r -n IOPMrootDomain -d1 | grep SleepDisabled`. No privilege is needed to read registry properties. Sleepless confirms "It sets IORegistry 'SleepDisabled' = Yes". **[D] Prefer this in-app (no subprocess). Compare it with the preference to detect a mismatch.**
- [C] Preference file: `CFPreferencesCopyValue("SystemPowerSettings", "com.apple.PowerManagement", kCFPreferencesAnyUser, kCFPreferencesCurrentHost)` is what `IOPMCopySystemPowerSettings` does (IOPMEnergyPrefs.c ~1604), and it is world-readable in practice ([U] not verified under the hardened runtime).
